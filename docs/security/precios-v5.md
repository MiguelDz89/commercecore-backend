# V5: persistencia de precios

La migración conserva los importes históricos de `sale_price` y establece `sale_price_configured=false` para todos los productos existentes y nuevos. El cero solo representa un precio confirmado cuando el indicador se establezca explícitamente en una futura operación autorizada. `cost_price` es opcional y no negativo. Los escalones tienen moneda implícita del producto, cantidad positiva `numeric(18,3)` y precio no negativo `numeric(18,2)`; PostgreSQL redondea entradas con mayor escala, por lo que la futura API debe validar precisión antes de escribir. Los UUID y la FK compuesta impiden referencias cruzadas; la unicidad cubre tenant, producto y cantidad. `updated_at` debe actualizarlo explícitamente la futura operación de aplicación.

V5 incorpora tres códigos de permiso sin asignarlos a roles. Su incorporación futura a perfiles requiere autorización explícita de plataforma, revisión de delegación y auditoría; no se conceden por inferencia ni se altera TENANT_ADMIN. El diseño de las futuras operaciones debe separar lectura y modificación de coste y escalones. No se debe exponer el coste ni los escalones en snapshots o consultas generales de auditoría: definir una consulta autorizada específica o almacenar referencias a eventos sensibles con control equivalente antes de implementar tales operaciones. No registrar secretos.

La migración no habilita endpoints ni variantes. Los valores de precios históricos requieren revisión comercial; la aplicación previa a V5 puede seguir escribiendo sale_price sin actualizar el indicador, por lo que debe desplegarse una versión compatible antes de usarlo como fuente comercial. Las escrituras SQL privilegiadas pueden eludir políticas de aplicación. Evaluar las reglas de moneda y conversión antes de permitir cambios de moneda.

Aplicar solo después de revisión y copia de seguridad, con la aplicación detenida y credenciales de migración apropiadas; comprobar que el destino sea la base autorizada, revisar el historial Flyway y ejecutar explícitamente la migración con el procedimiento operativo del entorno. No activar migración automática en desarrollo. La ejecución de pruebas utiliza exclusivamente PostgreSQL temporal.
